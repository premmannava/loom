This plan takes Loom from the 0.1 foundation to a 1.0 that can power a real application: a store whose screens are partly fixed and partly generated by a model while the user shops.

## Where things stand

**Done in 0.1:** the engine pipeline, parser with diagnostics, safe expressions, actions, keyboard focus, inspector, 12 components, 36 unit tests, the playground and the generated model guide.

**Missing for real apps:**

| Gap | Why it matters |
|---|---|
| State holds only single values | Products, carts and orders are lists of records |
| No way to repeat an element over a list | A catalog can't be written without it |
| No connection to real data | A model must never invent prices or stock |
| No host commands | "Add to cart" and "checkout" must run trusted app code |
| One screen per spec | Apps move between catalog, product, cart and checkout |
| No text input, images, scrolling, overlays | Search, product photos, long lists, dialogs |
| No accessibility layer | Screen readers can't see a canvas |
| No model connection | Everything is still simulated |

The phases below close these gaps in the order that unblocks the most.

## Phases at a glance

| Phase | Goal | Rough size |
|---|---|---|
| 1. Testing and tooling | Make every later change safe: CI, contract tests, fuzzing, visual regression, test helpers | 1–2 weeks |
| 2. Language 0.2 | Structured data, lists, grids, data sources, host commands, screens | 3–4 weeks |
| 3. Components and engine | Text input, images, scrolling, overlays, accessibility, about 20 components | 6–10 weeks |
| 4. The model loop | Real model writing specs live, repair loop, evaluations | 3–4 weeks |
| 5. Docs site | Documentation built with Loom, every example live | 2–3 weeks |
| 6. Loom Shop | A working store with generated discovery screens | 4–6 weeks |
| 7. Hardening and 1.0 | Performance, security review, npm release | ongoing |

Phases 4 and 5 can overlap with the end of Phase 3. The order follows the original plan (components, then docs, then the app), with the testing harness first and the model loop before the app, because the app depends on both.

## Phase 1: Testing and tooling

**Goal:** before the language and component set grow, make it cheap to catch regressions.

**Deliverables**

1. **CI** (GitHub Actions): typecheck, unit tests, build and visual tests on every push and pull request.
2. **Component contract tests** that run automatically over every registered component (details in [Testing strategy](#component-contract-tests)).
3. **Streaming and fuzz tests**: every prefix of every sample spec renders without errors; random and mutated specs never make the parser or engine throw.
4. **Visual regression**: Playwright renders every component example in light and dark at phone and desktop widths and compares against stored images.
5. **Test helpers** (`loom-ui/testing`), so interaction tests read like this:

   ```ts
   const ui = render(`state n=0\nbutton "Add" on=inc:n`);
   ui.press({ type: "button", text: "Add" });
   expect(ui.state.n).toBe(1);
   ```

6. **Docs generation**: `npm run docs:components` (already added) runs in CI and fails if the README is out of date.
7. **Benchmarks**: a 1,000-node and a 5,000-node spec, with timings recorded per commit.

**Exit criteria:** CI is green and required for merging; adding a component automatically gets it contract-tested and screenshotted.

## Phase 2: Language 0.2 (data, lists, screens)

**Goal:** make the language able to describe real applications, while keeping the three guarantees: streamable, safe, and design-free.

### 2.1 Structured data and property access

State and expressions gain lists and records:

```
text "{product.name}, ${product.price}"
text "{len(cart.items)} items"
```

- Property access (`a.b`, `a[0]`) works only on plain data (records and lists that came from state or sources), never on host objects or prototypes.
- New whitelisted functions: `len`, `sum(list, field)`, `money(amount, currency)`, `join`, `includes`, `lower`, `upper`.
- Input components that produce a value (stepper, slider, select) can pass it to an action as `$value`: `on="call:cart.set_qty(line: item.line_id, qty: $value)"`.
- The sandbox tests grow to cover `__proto__`, `constructor` and prototype tricks.

### 2.2 Lists: `each`

```
each items={products.data.items} as=p key={p.id}
  card
    text "{p.name}"
```

- `each` repeats its children once per item, with the item available under the `as` name. `key` keeps state and fade-in stable when the list changes.
- Streaming still works, because `each` is a normal container line.

### 2.3 Grid layout

```
grid min=220 gap=16
```

Columns are as many as fit at `min` width each, so the same spec works on a phone (1 column) and a desktop (4 columns).

### 2.4 Data sources: real data the model can't invent

The host app registers named, typed **sources**. A spec can only read data through them:

```
state query="trail shoes" maxPrice=120
source products from=catalog.search query={query} max_price={maxPrice}
```

- Like `state`, `source` lines are unindented declarations, usually at the top. A source can be conditional: `source product from=catalog.get id={selected} if={selected != null}`.
- `{products.data}`, `{products.loading}` and `{products.error}` are available to expressions.
- When a parameter changes (the user types a new query), the engine calls the source again, debounced.
- Sources are described in the model guide from their registered schemas, the same way components are, so the model knows exactly what data exists.
- Unknown sources or parameters are diagnostics, like unknown components.

### 2.5 Host commands: trusted actions

The host registers **commands** for anything with real effects. Specs call them with `call:`:

```
button "Add to cart" on="call:cart.add(id: p.id, size: size, qty: 1)"
```

- Arguments are expressions, checked against the command's schema.
- Commands declare which sources they make stale (`cart.add` refreshes `cart.get`), so the screen updates without the model being involved.
- Commands that move money or share personal data require `confirm: true` in their registration. The engine then shows a confirmation step that the spec can't skip or restyle.
- Commands can be marked `fixedScreensOnly: true`. Only specs loaded with `setSpec(spec, { trusted: true })` (reviewed by a person) can call them; generated specs can't.

### 2.6 Screens and navigation

```
screen name=catalog title="Shop"
  ...
screen name=product title="{product.data.name}"
  ...
```

- Actions `go:product` and `back` switch screens, with history. The current screen is available as `{screen}`.
- Only the active screen is laid out and painted. The first screen is shown by default.

### 2.7 Notifications

`notify:'Added {p.name} to your cart'` shows a short toast message. The text, position and look are controlled by the engine.

**Exit criteria:** the catalog and product screens in [the ecommerce example](examples/ecommerce.md) parse, render (with placeholder components where Phase 3 hasn't landed) and pass streaming tests. The model guide documents sources and commands generated from their registrations.

## Phase 3: Components and engine capabilities

**Goal:** the component set and engine features a real app needs. Every component follows [How components get made](#how-components-get-made).

### 3.1 Engine capabilities (built first, because components depend on them)

| Capability | Approach |
|---|---|
| **Text input** | While a field is focused, place a real, transparent `<input>` exactly over its box. The browser handles typing, IME for other languages, autocorrect, password managers and mobile keyboards. Loom paints the field and mirrors its value. |
| **Images** | Async loading with placeholder and fade-in, a cache, `ratio=` to reserve space before load, and an allowlist of image hosts. CORS-enabled images only, so the canvas stays readable for tests. |
| **Scrolling** | Scroll containers that clip children, handle wheel, touch and keyboard scrolling, and only lay out what is visible (virtualization) for long lists. |
| **Overlays** | A layer above the page for dialogs, dropdowns, tooltips and toasts, with focus trapping and Escape to close. |
| **Accessibility mirror** | A hidden DOM tree that mirrors the canvas: a role, a label and a state for each element, focus kept in sync, and live regions so screen readers hear updates. Same idea as Flutter's semantics tree. |
| **Pointer gestures** | Drag for sliders and scroll areas, long press, and touch targets at least 44 px. |

### 3.2 Components

**Tier A, needed for the store (in this order):** `input`, `image`, `grid` (Phase 2), `badge`, `select` and `option`, `stepper`, `slider`, `radio`, `switch`, `tabs`, `list` and `list-item`, `rating`, `skeleton` (loading), `empty` (empty state), `link`. Also: `card` becomes pressable when given `on=`, and `text` gains `strike=` for old prices.

**Tier B, needed for dashboards and docs:** `table`, `chart` (bar, line), `dialog`, `menu`, `tooltip`, `accordion`, `avatar`, `pagination`, `breadcrumb`, `slider`, `code` (for the docs site).

**Tier C, later:** `date-picker`, `autocomplete`, `file-upload`, virtualized `data-table`, `rich-text`.

**Exit criteria:** Tier A and the engine capabilities are done, with contract tests, visual baselines and docs. The accessibility mirror passes an automated audit (axe) on all samples. A screen reader can complete the store's add-to-cart flow (tested by hand with VoiceOver and NVDA).

## Phase 4: The model loop (UI on the fly)

**Goal:** a real model generates Loom while the user watches, and the user's actions flow back.

### 4.1 Architecture

```
 Browser                        Your server                     Model
┌───────────────────┐   1  ┌──────────────────────┐   2   ┌───────────┐
│ user message      │ ───► │ build prompt:        │ ────► │           │
│                   │      │  language guide      │       │           │
│                   │      │  sources & commands  │  3    │           │
│                   │      │  conversation        │ ◄──── │ tool calls│
│                   │      │ run tools (search…)  │ ────► │           │
│ loom.push(chunk)  │ ◄─── │ stream Loom text     │ ◄──── │ Loom text │
│                   │  4   │ validate; repair     │   5   │           │
│ emit → message    │ ───► │ next turn            │       │           │
│ call → command    │ ───► │ run command directly │       └───────────┘
└───────────────────┘      └──────────────────────┘
```

1. The user asks for something ("trail shoes for wet weather under $120").
2. The server sends the model a system prompt built from `languageGuide()` plus the registered sources and commands, and the conversation so far.
3. The model may call tools first (search the catalog) to decide what to show. Tool results never go into the spec as text. The spec reads them through sources, so prices and stock always come from the store's systems.
4. The model streams Loom. The server forwards each chunk to the browser (server-sent events), and `loom.push()` renders line by line.
5. When the stream ends, the server parses the spec with the same parser. If there are errors, it sends the diagnostics back to the model once and asks for a corrected spec, then swaps it in.

User actions take two different paths:

- **`emit:`** goes back to the model as the next conversation turn ("the user chose the Gore-Tex pair, size 10"). Use it when the next screen needs the model's judgment.
- **`call:`** runs a host command directly, with no model involved. Use it for everything deterministic: add to cart, change quantity, pay.

### 4.2 Deliverables

1. A small server package (`loom-ui/server`) with: building the prompt from registries, streaming to the browser, validation and one repair attempt, and per-session rate limits.
2. A client helper (`loom-ui/client`) that connects a `Loom` instance to the stream and turns `emit` events into messages.
3. **Commerce rules for the parser** (`rules: ["commerce"]`): no currency amounts written as text (prices must come from `{…}` reading a source), no arithmetic on prices, and no calls to `fixedScreensOnly` commands from generated screens. The full list is in [the ecommerce example](examples/ecommerce.md#safety-rules-for-commerce).
4. **Patches**: give elements an `id=`, so the model can update part of a screen ("replace `#results`") instead of regenerating all of it.
5. **Templates**: reviewed specs for common screens that the model fills in with parameters, which is faster and safer than writing from scratch.
6. **Evaluations** (see [Model evaluations](#model-evaluations)) run on every change to the guide or language.

### 4.3 What a model may and may not do

| A model may | A model may not |
|---|---|
| Choose and arrange components | Register components or run code |
| Read data through registered sources | Write prices, stock or order details as literal text |
| Call registered commands through buttons | Skip confirmation on money-moving commands |
| Ask for the user's next choice with `emit` | Generate payment or login forms (those are fixed, reviewed screens) |

**Exit criteria:** on the evaluation set, at least 95% of generated specs have no errors after one repair, the first line is on screen within about a second of the model starting to answer, and token counts are measured against JSON-based formats (A2UI, json-render) for the same screens.

## Phase 5: Docs site

**Goal:** documentation that is itself a Loom showcase.

- Built with Loom, using Tier B components (`code`, `tabs`, `table`, `link`).
- Every component page is generated from its `ComponentDef`: description, props table and a live, editable example.
- Pages: getting started, the language, components, sources and commands, connecting a model, theming, debugging, and the store walkthrough.
- A "try it" page where visitors type a prompt and watch a model build a screen (rate-limited, behind the Phase 4 server).
- Search, light and dark mode, and an accessible version through the mirror.

**Exit criteria:** the site is deployed, every example on it is live, and docs are rebuilt in CI from the component definitions.

## Phase 6: Loom Shop, the reference app

**Goal:** prove Loom can run a real, complete product. The full design is in [`docs/examples/ecommerce.md`](examples/ecommerce.md).

**Split between fixed and generated screens:**

| Screen | Made by | Why |
|---|---|---|
| Catalog, search, filters | Fixed template | Fast, predictable, indexable |
| Product page | Fixed template | Same layout for every product |
| Cart | Fixed template | Money; must be exact and reviewed |
| Checkout and payment | Fixed template plus hosted payment page | Payment details never pass through Loom |
| Order confirmation | Fixed template | Legal and support requirements |
| Shopping assistant answers | **Generated on the fly** | "Compare these two", "what goes with this?", "gift ideas under $50" |
| Promotional and seasonal pages | **Generated, then reviewed** before going live | Saves design time, keeps control |

**Backend:** a catalog API (search, get), cart API, order API, and a payment provider's hosted checkout. Loom registers these as sources and commands.

**Exit criteria:** a user can search, compare products with the assistant, add to cart, pay through the hosted checkout (in test mode) and see their order. The full flow works by keyboard and screen reader. Analytics compare assistant-generated screens with fixed ones on add-to-cart rate.

## Phase 7: Hardening and 1.0

- **Performance:** repaint only changed regions, cache text layout, virtualize everything that scrolls. Budget: 60 frames per second while scrolling a 5,000-item list on a mid-range phone.
- **Security review:** the expression sandbox, spec size and depth limits, source and command rate limits, image host allowlists, and content security policy guidance.
  - Found in Phase 1: the engine overflows the call stack on specs nested somewhere between 500 and 2,000 levels deep, because layout and paint are recursive (the parser itself is fine). A nesting limit in the parser, reported as a diagnostic that skips deeper lines, would turn this into an ordinary error.
- **Internationalization:** right-to-left layout, number and currency formatting by locale, and font fallback for other scripts.
- **Native renderer experiment:** run the same engine in Rust with WebAssembly for heavy screens, and as a native app outside the browser (see the speed discussion in the README).
- **Release:** publish `loom-ui` to npm with semantic versioning and a changelog, and a migration guide for language changes.

## How components get made

Components are always reviewed code. Models generate **specs** at runtime, never components.

### The pipeline

1. **Proposal.** Write a short note: the component's name, what a model would use it for (one or two sentences, which becomes its `description`), its props, and an example spec. Check it doesn't overlap an existing component.
2. **Scaffold.** `npm run new:component badge` (Phase 1 tooling) creates `src/components/badge.ts`, a test file and a playground sample from a template.
3. **Implement** `layout`, `paint`, and if needed `hitTest` and `press`, using only theme tokens. Follow [`CLAUDE.md`](../CLAUDE.md).
4. **Test.** Contract tests run automatically. Add behavior tests for anything specific, then create the visual baseline.
5. **Document.** `npm run docs:components` updates the README; the docs site and model guide pick it up automatically.
6. **Evaluate.** Add at least three prompts to the evaluation set where the component should be used, and check that models pick it and use its props correctly. If they don't, improve the `description` and `example`, not the prompt.

### Using AI to draft components

A model is good at drafting a `ComponentDef` from a proposal. Give it [`CLAUDE.md`](../CLAUDE.md), the `ComponentDef` contract in `src/component.ts`, one similar existing component as a reference, and the proposal. Then the contract tests, visual baselines and a human review decide whether it ships. The tests exist precisely so that AI-drafted components can't quietly break the rules.

### Definition of done for a component

- [ ] Every prop has a type, description and default (or is required)
- [ ] The example parses with no diagnostics
- [ ] Contract tests pass (layout at 320, 600 and 1024 px; no overflow; theme tokens only)
- [ ] Visual baselines in light and dark
- [ ] Keyboard reachable and operable, if interactive
- [ ] Accessibility mirror role and label (from Phase 3)
- [ ] Docs regenerated
- [ ] Evaluation prompts added

## Testing strategy

Loom is tested in layers, from fast and exact to slow and statistical.

| Layer | Tool | Runs | Catches |
|---|---|---|---|
| Unit | Vitest | Every save | Parser, expressions, actions, layout math |
| Component contract | Vitest over the registry | Every push | A component breaking a project rule |
| Streaming and fuzz | Vitest + fast-check | Every push | Crashes on partial or odd input |
| Interaction | Vitest + `loom-ui/testing` | Every push | Presses and state changes |
| Visual regression | Playwright + pixelmatch | Every push | Anything that looks different |
| Accessibility | axe-core on the mirror, plus manual screen reader passes | Every push, manual per release | Missing roles, labels, focus problems |
| Performance | Benchmark specs | Every push | Slowdowns over 20% |
| Model evaluations | Evaluation runner | When the guide or language changes | Models writing bad or unsafe specs |
| Security | Sandbox escape suite | Every push | Expressions reaching JavaScript |

### Component contract tests

For every registered component, automatically:

1. Its `example` parses with no diagnostics.
2. Every prop has a description; enum defaults are among the allowed values.
3. Laid out at 320, 600 and 1024 px wide, no child box extends past its parent and every height is finite and non-negative.
4. Painting with a recording canvas uses only colors that exist in the theme.
5. Interactive components register a hit region and can be reached with Tab.

### Streaming and fuzz tests

- For every sample spec, every prefix cut at a line boundary parses without errors, and each prefix's tree is the beginning of the next one's (nothing jumps around while streaming).
- Random specs built from the grammar, plus real specs with random characters deleted, inserted or swapped: the parser and engine never throw, and every problem has a line number.

### Visual regression

Render each component example and each sample in light and dark at 375 and 1024 px, compare against baseline images with a small tolerance, and upload a diff image in CI when something changes. Baselines are updated deliberately in the same pull request as the change.

### Model evaluations

An evaluation set of about 100 prompts in categories (forms, comparisons, dashboards, shopping, edge cases like "make the button red"). For each model and guide version, record:

| Metric | Target |
|---|---|
| Specs with no errors on the first try | Above 90% |
| Specs with no errors after one repair | Above 98% |
| Warnings per spec | Falling over time |
| Output tokens per screen | Compared with A2UI and json-render for the same screens |
| Time to first rendered line | About a second |
| Task success (scripted: the expected button exists and calls the right command) | Above 90% |
| Rule violations (literal prices, unknown sources, payment calls from generated screens) | Zero |

## Open questions

These are decisions to make during the phases above, not now.

1. **Patches or full regeneration** for updates in Phase 4. Patches are faster and cheaper but add syntax for models to learn. Measure both in the evaluations.
2. **Object literals in expressions.** Named command arguments (`id: p.id`) may be enough. Avoid general objects unless evaluations show models need them.
3. **Fixed screens in Loom or in the host framework.** The store plan uses Loom for all screens to prove the engine. A real merchant might keep checkout in their existing framework.
4. **Server-side rendering.** Search engines can't read a canvas. Options: generate HTML for crawlers from the same tree, or keep indexable pages (catalog, product) outside Loom.
5. **Native renderer timing.** Only worth it once screens are heavy enough for the browser to be the bottleneck, which the speed measurements say is not yet the case.
6. **A DOM render target.** A second renderer that builds plain DOM elements (no React or Angular) from the same parsed tree, state and actions. The language, parser, expressions, actions and model guide would be unchanged; only the drawing step would differ. This is not planned: rendering stays on the canvas ([`CLAUDE.md`](../CLAUDE.md), rule 7). It is recorded here so the tradeoff can be measured rather than argued.

   | Gains | Costs |
   |---|---|
   | Accessibility, text input, IME, autofill, text selection, copy and browser find come from the browser almost for free | A second implementation (`dom` alongside `layout` and `paint`) for every component, kept in step forever |
   | Search engines can read the page (see question 4) | Browser layout won't exactly match the canvas layout, so the same spec can look different in each target |
   | Scrolling, overlays and focus handling are native | The debugging tools (layout boxes, hit regions, inspect mode, frame capture) are built on canvas boxes and don't carry over |

   Updates would also need care. Today the engine doesn't track which expressions read which state: any state change re-lays out the whole tree (`src/engine.ts`, the `state.subscribe` handler calls `invalidate("layout")`). `identifiers()` in `src/expr.ts` can list the names an expression reads, but nothing uses it for dependency tracking yet. A DOM target that updates only changed elements would need that tracking built first. (The canvas engine could use the same tracking to skip re-layout.)

   **Candidate spike after Phase 1:** on a branch, build DOM versions of three components (`text`, `button`, `check`) and record the effort and the code each needs. Compare that with the estimated effort of the accessibility mirror (Phase 3.1) for the same components, then decide whether to go further, stop, or revisit after the mirror exists.
